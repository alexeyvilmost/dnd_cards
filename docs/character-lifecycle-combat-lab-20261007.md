# Коллекция персонажей и тестовый бой

Страница `/characters-forge` объединяет интерактивные и бумажные листы. По умолчанию открыты стандартные персонажи; отдельные вкладки показывают листы забегов, бумажные документы, общую коллекцию и шаблоны. Прежние адреса бумажного редактора сохранены. Главная страница ведёт в библиотеку, коллекцию персонажей и забеги.

Удаление стандартного персонажа сохраняет его историческую запись и внешние ссылки. Если он участвует в онлайн-сражении, транзакция блокирует сначала встречу, затем лист, удаляет только его токен из текущего состава и добавляет событие в журнал. Прежние события не изменяются. Изменение привязки встречи во время удаления возвращает конфликт для повторного запроса.

Удаление забега или его персонажа скрывает весь забег и принадлежащие ему игровые листы. Повторно используемые исходные персонажи остаются. Забег из шаблона сразу создаёт игровой лист, без промежуточного стандартного персонажа; `source_template_id` сохраняется, а FK источника ссылается на этот игровой лист.

`/combat-lab` создаёт тестовую сцену на копиях собственных персонажей. Страница использует обычный `SoloCombatPage`, каноничный сборщик участников, действия, броски и диалоги. Конструктор позволяет менять карту, добавлять персонажей и противников, восстанавливать ресурсы и менять инициативу. Во время редактирования сцены ИИ приостановлен; ожидающие решения блокируют изменение сцены. Состояние, участники и ожидающие решения сохраняются в браузере, без команд изменения исходных листов или забегов.

Предметы без веса и внешнего объёма занимают ноль соответствующей вместимости контейнера. Неизвестная карточка, некорректное отрицательное значение, цикл вложения и специальные ограничения жидкости по-прежнему требуют корректных данных.

ИИ проверяет запрет действия и движения до выполнения команды; обездвиженный противник завершает ход и выполняет положенные проверки завершения эффектов. Этот код применяется к новым боям. Уже сохранённые серверные бои продолжают использовать свой прежний исполняемый артефакт; выпуск не подменяет артефакт, не пересчитывает прошлые броски и не обновляет молча старые каталоги.

## Выпуск и сохранность данных

После ошибки серверного боя игрок может явно выбрать «Обновить правила этого боя» и подтвердить отдельный диалог. Команда `upgrade_combat_rules` разрешена только в активном бою на ходу управляемого персонажа, без ожидающих решений и движения, с совместимыми solo/world schema 1/5. Worker проверяет наличие и SHA прежнего executable, выбирает только собственный текущий SHA, валидирует копию world, но не сохраняет результат нормализации. Backend сравнивает весь frame с исходным: допустима только замена artifactHash; ресурсы, хиты, каталог, world, log, seed/cursor и runtime revision не меняются. Транзакция CAS увеличивает только ревизию забега, добавляет приватный baseline нового сегмента, точный previousBaseline и связь с прежним сегментом/последним событием, сохраняет квитанцию. Повтор с тем же ID не выполняет команду снова. UI сохраняет только ID/ревизию неопределённой команды и повторяет их после перезагрузки. Прежние артефакты и события не переписываются; автоматически это действие не выполняется. Граница обновления проверяется replay-читателем и сохраняет формат schema 1, читаемый прежним reader.

Аддитивная схема `301_character_lifecycle` добавляет только nullable `deleted_at` в `characters_v3` и `roguelike_runs` и два индекса. Release SDK проверяет точные типы, nullable, индексы и транзакционность DDL/ledger. Историческая проекция исключает только новый столбец, если его ещё не было в исходной схеме; все прежние столбцы и таблицы остаются в проверке.

При включённых compact receipts и image jobs разрешён только переход с неизменными протоколами, прежними migration identities и writer flags, добавляющий точную проверенную 301. Это разрешение построить кандидата. Для применения обязательны свежие exact-image migration approval, полный history restore, проверки прежнего и нового readers/writers, pending/retry/jobs и rollback. SDK учитывает существующие форматы 298/300 только при таком точном исходном наборе; неизвестный формат и ссылка frozen catalog по-прежнему запрещают откат. Прежние исходники 298/299/300 не меняются. Строка протокола `additive-298-300` сохранена для совместимости с прежними отчётами; перечень допустимых исполнителей явный, включает 301.

Исправление количества целей «Жуткого смеха Таши» является изменением данных, а не схемы. Отдельный оператор `scripts/content/repair-laughter-targeting-20261007.mjs` по умолчанию показывает план без записи. Применение требует точного свежего `beforeHash` и абсолютного пути нового приватного архива. Транзакция блокирует единственную карточку, проверяет полный preimage, задаёт базовые min/max=1, сохраняет повышение уровня и прочие данные, ставит `not_verified`. Изменённая вручную декларация max не перезаписывается. Проверяются точный postimage и неизменность сохранённых каталогов и исторических боевых данных; конфликт откатывает всю транзакцию. Архив не перезаписывается, при неопределённом результате автоматический повтор запрещён.

Пример запуска через приватно переданный `DATABASE_URL`:

```text
node scripts/content/repair-laughter-targeting-20261007.mjs
node scripts/content/repair-laughter-targeting-20261007.mjs --apply --expected-before=sha256:<свежий-хэш> --archive=<абсолютный-приватный-путь>
```

Нельзя использовать хэш локальной копии для production. Контент-операция выполняется отдельно от schema executor после согласования выпуска с соседним рабочим деревом. Production БД не заменяется локальным дампом.

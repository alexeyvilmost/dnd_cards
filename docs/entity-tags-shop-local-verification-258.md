# Теги сущностей и магазин забега — локальная проверка 258

## Что доступно

- Библиотека: «Фильтр по тегу» и «Справочник тегов» с поиском и созданием новых меток администратором. Фильтрация выполняется в БД до пагинации; ссылка сохраняет выбранный тег.
- При выключенном «Режиме игрока» детальное окно сущности показывает теги. Администратор может назначать и снимать их, создавать новые. В бестиарии и конструкторе переключаемых пассивов используется тот же механизм.
- Предмет: в этом же окне есть «Параметры товара забега»: минимальный уровень, вес при выборе, количество в пачке, необязательная цена пачки и категория добычи.
- На странице забегов и в магазине администратору доступна кнопка «Настройки магазина забега».
- Для каждого уровня 1–5 задаются число случайных товаров, верхний лимит магических товаров и независимые от названий предметов шансы необычной/редкой/эпической редкости. `very_rare` соответствует эпической.
- Шанс бросается на каждый свободный слот. Резерв сохраняется и учитывается в лимите. Истощённая редкость заменяется обычным товаром; если обычных нет, слот пустует, но остальные броски всё равно происходят. Скрытого возврата к старому ассортименту нет.
- Стартовая экипировка доступна за имеющееся золото до первой победы. Она выделена в отдельный раздел. Базовые товары доступны без ограничения числа покупок; для каждой покупки проверяются деньги и грузоподъёмность. Цены припасов и обновления тоже хранятся в настройках.
- Цена из карточки переводится в целые золотые с округлением вверх за пачку, поскольку кошелёк забега использует целое золото. Необязательная цена пачки задаётся в золотых и имеет приоритет. Размер пачки не меняет количество единиц добычи за награду.

## Перенос и совместимость

`258_entity_tags_shop` создаёт справочник, назначения, конфигурацию магазина и правила товаров. Исходные настройки редкостей сохранены: 0.5%; 1.25%/0.1%; 2.1%/0.5%; 3%/1.25%/0.1%; на пятом уровне повторяются настройки четвёртого.

В рабочей локальной БД перенесены 207 старых записей. Исходные массивы, в том числе дубли, сохранены в `legacy_entity_tags_258`. Новые назначения дедуплицированы. Начальные пулы: 49 предметов забега, 3 базовых товара, 117 позиций стартовой экипировки. Удалён старый свободный ввод `TagsInput`; старые обработчики записи меток и их использование для категории оружия/скидок удалены. Категории оружия берутся из профиля и общего справочника типов; серверная копия справочника проверяется тестом на совпадение с каноническим JSON фронтенда.

Старые сертификаты хешировали в том числе `tags: null`. Поэтому колонки переименованы в `legacy_tags`, а модели читают их только для совместимого wire-снимка `tags`. Новая система их не меняет и не использует для фильтров/механики. Сертификаты не пересчитывались и не выдавались повторно. Проверены исходные контрольные суммы 15 базовых состояний. Новый произвольный тег не меняет исполнение сущности.

Сохранённые магазины, резервы, чеки команд, персонажи и боевые журналы не мигрируются в новый ассортимент. Новые настройки применяются при следующей генерации магазина. API настроек защищён версией от потерянных обновлений.

## Локальный запуск и резервные копии

Локально: UI `http://localhost:3001`, API 8080, worker 8090; рабочая БД `shop_review_249_20260915` на loopback:5434. Запуск API — `scripts/roguelike/start-tags-local.ps1`, с явным именем рабочей БД.

В исходном environment-файле оказалось другое имя БД (`dnd_cards`). После обнаружения несоответствия рабочий запуск исправлен. Неактивная БД восстановлена из сделанного до изменений дампа; её изменённая копия сохранена отдельно как `dnd_cards_tags_258_recovery`, ничего из неё не удалено. Дампы: `outputs/entity-tags-258/before.dump` (неактивная база) и `working-before.dump` (рабочая база). Во время локальной доработки совместимых wire-полей использован `preserve-tags-wire-local.ps1`; для будущей выкладки достаточно итоговой миграции 258, этот локальный корректирующий скрипт не нужен.

Прод не изменён; коммит и push не выполнялись. Перед будущей выкладкой нужны свежий prod-backup и согласованный переход приложения/БД. Автоматического разрушительного Down нет: архив и новые данные сохраняются; откат версии приложения следует планировать вместе с её схемой БД.

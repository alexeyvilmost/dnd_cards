# Задержка commands в групповом бою — 8 октября 2026

Проверен бой из обращения владельца: забег `5a9f10b1-885f-40e3-ba78-45ec11f62590`, четыре персонажа. Первоначальные production-замеры относятся к релизу `24866cda598536247ce99bbf389e84abf24c7bbb`. Рабочая БД и бой не изменялись. Снимок и закреплённый исполняемый артефакт скопированы в закрытый локальный каталог; игровые команды выполнялись только на копиях.

## Что тормозит

Это сочетание дорогих ходов ИИ и обработки многомегабайтного JSON. Задержка не объясняется только интернетом или загрузкой картинок: журнал backend подтверждает 1,93–3,16 секунды обработки тех же пяти запросов, Caddy — 1,93–3,17 секунды.

SQL-время включает передачу и декодирование строк клиентом. Оно входит в транзакцию и другие интервалы; столбцы нельзя складывать как независимые стадии. Локальный runner использует исходную игровую сцену, каталог и артефакт, но изолированную БД, тестового владельца и локальный HTTP без production gzip. Это воспроизведение проблемы, а не гарантия будущей задержки на TimeWeb.

Самый длинный запрос соответствует `end_turn`, ревизии 28. Весь журнал воспроизведён: 30 кадров, совпадение before/after-хэшей и случайных значений. Именно этот переход занял локально 487–833 мс под CPU-профилировщиком; отдельное выполнение на процессоре TimeWeb — 1544 мс. Последнее измерение сделано отдельным Node-процессом и включает холодный JIT; оно не заменяет трассировку исходного HTTP-запроса.

В CPU-профиле завершения хода первая функция по числу семплов — `sha256String`, далее `projectCombatAuras` и `canonicalStringify`. В `stepRoguelikeCombat` после каждого хода противника выполняются два `canonicalSha256Sync` всего состояния для проверки прогресса ИИ. Это браузерная реализация SHA-256 на JavaScript; она хэширует в том числе большой журнал и оформление. Переключение на следующий ход может исполнить несколько ходов противников. Поэтому `end_turn` существенно дороже отдельного спасброска.

Дополнительные затраты:

- `ownedRoguelikeRun` вызывается до worker, при блокировке и после сохранения. Ранее каждый вызов отдельно загружал главного персонажа, а затем снова загружал его в составе группы.
- При выключенном `DB_FROZEN_CATALOGS` обработчик повторно записывал неизменившиеся inline-каталог, checkpoint и другие холодные колонки. В данном запросе это 761 322 байта.
- Worker получает `envelope`, `character` и `characters`. Главный персонаж повторяется, а его `turn_state.solo_combat_v1` содержит ещё один снимок сцены.
- Ответ API содержит `combat_state`, главного `character` и того же главного персонажа в `characters`; сцена повторяется в сохранённом turn state. Gzip уменьшает передачу, но не устраняет серверные обходы, копирование, разбор и сохранение этих объектов.
- Между backend и worker уже включён `mirrors-v2`, но Go восстанавливает полный JSON через несколько разборов и сериализаций. На копии это около 77–96 мс только для восстановления, до следующего разбора результата.

## Первые локальные изменения

1. Главный персонаж группы загружается вместе с остальными участниками одним запросом. Загрузка одиночного персонажа, порядок группы, права владельца и блокировки проверены.
2. Сравнение холодных колонок работает и для inline-каталогов, независимо от экспериментального хранения frozen catalogs. Изменившиеся данные продолжают сохраняться; формат БД не меняется.

На том же локальном сценарии: 19 → 16 SQL-операций, медиана SQL 370 → 276 мс, транзакции 452 → 399 мс, полного запроса 899 → 841 мс, то есть примерно **6,4%**. Выборка мала: пять прогретых запросов на вариант. Холодный первый запрос остаётся около 1,3 секунды. Эти изменения полезны, но **не решают всю задержку в три секунды**.

Две группы обязательных Go-проверок прошли без пропусков: десять различных тестов, включая блокировки/владение, frozen readers, сохранение изменившегося каталога, идемпотентность, rollback и worker mirrors. Локальный API проверен шестью командами и шестью точными повторами для каждого варианта. На одном первом запуске все Go-тесты прошли, но Go вернул ошибку удаления временного EXE в Windows; повтор в принадлежащем runner каталоге завершился с кодом 0. Воспроизведение журнала потребовало стандартного `go-json-map-v1` порядка ключей; исходные данные не исправлялись.

## Первоначальные предложения (статус уточнён ниже)

1. **Хэширование worker.** Добавить проверенный нативный SHA-256 для Node при неизменной канонизации; браузеру оставить совместимую реализацию. Сравнить хэши на Unicode, больших объектах, всей истории этого боя и вторых сценах. Выпустить новый артефакт. Текущие закреплённые бои сохраняют старый исполнитель; переход — только через существующую явную команду обновления правил, когда нет открытого решения.
2. **Компактный транспорт API.** Передавать сцену и главного персонажа по одному разу, с явными ссылками только внутри одного ответа. Адаптер восстанавливает прежний каноничный DTO. Согласовать протокол заголовком; старые клиенты получают полный ответ. Не опираться на предыдущий кадр/кэш браузера. Не менять исторические квитанции.
3. **Компактный ввод и разбор worker.** Отделить данные проекции листа от старого полного снимка в turn state; подтвердить точное равенство результатов на всех поддержанных архивных артефактах либо использовать объявленную capability. Восстанавливать `mirrors-v2` в типизированный результат без цепочки полных JSON-пересериализаций. Проверки ссылок и целостности оставить обязательными.
4. **Чтение после сохранения.** Проверить построение ответа из уже заблокированного и сохранённого агрегата вместо полной повторной загрузки. До включения сравнить с обычным GET: все поля, временные метки, декорации доступа, выводы БД, одиночный/групповой бой, rollback, повтор и конкуренция.
5. **Пространственная проекция ИИ.** Уменьшить повторные пересчёты пар участников/света/аур в рамках одной неизменившейся доски. Инвалидация должна учитывать движение, жизненное состояние, эффекты, ресурсы и подавление магии. Не кэшировать только по номеру хода и не менять вычисления старого артефакта.

После каждого этапа — одинаковая копия ревизии 28 и сценарии move/action/death_save, отдельно первый и прогретые запросы, минимум 30 повторов, совпадение игровых результатов и отказов, точный retry/reload, затем ограниченный production замер. Уточнённая пользователем цель приёмки — полный ход до 200 мс на TimeWeb, желательно около 100 мс, включая `end_turn`. Это целевой критерий, а не уже достигнутый результат.

## Реализация после разрешения на асинхронное сохранение

Пользователь разрешил потерю последнего хода при аварийном завершении процесса. Реализация использует более строгую границу: в каждом забеге может быть максимум одна принятая, ещё не сохранённая команда. Следующая команда ждёт атомарного commit предыдущей. Инициализация, смена правил, завершение боя и экономика сохраняются до ответа. Перед ранним ответом проверяются владелец, ревизии и временные метки всех участников; соответствующие строки уже заблокированы PostgreSQL. Изменения листов, снимок, журнал и точная квитанция пишутся одной фоновой транзакцией. Ошибка записи откатывает её полностью, очищает недостоверный кадр и блокирует новые команды до загрузки сохранённого боя. При штатном завершении сервер ждёт сохранений.

Кэш бекенда хранит актуальный снимок и замороженный каталог действий/эффектов; прогревается после инициализации и фоновым чтением последних восьми активных боёв при запуске. Каждая команда проверяет лёгкие метаданные PostgreSQL, чтобы изменения из другой вкладки/процесса не потерялись. Остаются обязательные запросы к БД для контроля владельца и ревизии; их нельзя заменить устаревшим локальным разрешением.

Worker хранит до 16 кадров / 64 МиБ. Прогретый запрос данного боя уменьшился с 4,36 МБ до примерно 86 КБ. Листы передаются без старого вложенного снимка только для двух точно распознанных проекторов; неизвестная версия получает полный ввод. Промах кэша определяется до выполнения команды, после чего бекенд отправляет полный кадр. Протокол браузера combat-frame-v1 передаёт лидера один раз и восстанавливает ссылки внутри того же ответа. Различия оформления сохраняются, предыдущий кадр браузера не нужен. Исторические квитанции остаются полными.

В отдельном worker thread заранее вычисляется универсальная команда end_turn для текущего подконтрольного участника. Это существующий чистый переход закреплённого движка: результат используется только при совпадении полного beforeHash, версии артефакта и всей команды. Предварительный расчёт не меняет состояние, не расходует ресурсы и не продвигает сохранённый RNG. Кэш результатов ограничен восемью / 32 МиБ; ошибка, рестарт или промах дают обычное исполнение.

Для строго распознанных функций CJS применяются эквивалентные оптимизации исполнения: native SHA-256, мемоизация чистых проверок жизнеспособности только внутри пространственной проекции неизменившейся доски, сравнение действительно изменяемых полей копий участников и дешёвое доказательство прогресса по полям инициативы перед полным хэшированием. Контрольные суммы всех распознаваемых функций обязательны. Неизвестные реализации исполняются без этих замен. Байты и идентификаторы архивных артефактов не переписываются. Все 30 кадров исходного журнала совпали с оригинальным исполнением, включая RNG и хэши.

Профилирование включается для commands автоматически: Server-Timing и X-Performance-Metrics разделяют очередь, SQL, кэш, передачу, вычисление/попадание предварительного расчёта, проекцию и декодирование. Фоновая запись журналируется отдельно с request_id, итогом и длительностью; игровые данные и секреты в неё не попадают.

Последняя локальная проверка: 50 реальных команд на копии исходного боя, 50 точных повторов, полное равенство ответа обычному GET, сохранённых кадров журналу и исходных артефактов прежним байтам. Проверки включают rollback фонового сохранения, блокировку следующей команды, сброс после загрузки, отсутствие частичных записей, приватность wire, чужого владельца и вторую сущность.

# PERF-03 — длинная легальная последовательность: история, payload и память

Локальное измерение 05.10.2026 завершено: **160 команд PASS**, затем
**100 команд PASS** для точного разбора роста по полям. В обоих запусках каждая
принятая команда проверена точным API retry и повтором **всего** сохранённого
worker input с полным равенством worker result. Cleanup завершён, исходные
персонажи не изменены. [Числовые окна и hashes доказательств](PERF-03-long-combat.json).

## Сценарий и полнота повторов

Отдельный dbOnly стенд создаёт персонажа `line` обычным API. В собственном
synthetic каталоге урон двух доступных учебных противников объявлен нулевым
**до initialize**; обычные атаки, броски и AI сохраняются. До initialize также
выбрана сцена `clearing-v1`, map seed7. После freeze каталожные декларации
восстановлены через API с перечитыванием. Сохранённые RNG, runtime и исходы
после начала боя не редактируются.

В фактически выбранном столкновении один персонаж и один противник. Все160
команд основного запуска — легальные `end_turn`: бой прошёл с раунда1 до161
и оставался активным. Противник действительно атаковал: RNG cursor2→162,
последовательность истории4→805. Основной цикл занял92.8с, диагностический100
команд —58.9с. Это wall time драйвера с SQL-проверками и replay, не API p95.

На каждой команде checked revision+1, точный receipt response, неизменность
хэшей полного run/character и счётчиков БД после retry. Отдельный прямой worker
replay возвращает тот же полный результат на тех же JSON-байтах входа; seed,
ID, events и trace не нормализуются. Повтор через API не вызывает worker снова.
Полные состояния и авторизационные данные остаются в памяти. Raw reports в
owned outputs содержат только числа, hashes и идентификаторы тестовых команд;
их SHA-256 и пути включены в компактный JSON.

## Точный источник оставшегося роста

Повторный `test_889cd2171abd6190096c6441` измерил bytes/count каждого world/scene
поля и агрегированные размеры полей actors, без сохранения их содержимого.
За100 ходов `world` вырос42503→62116B, то есть на19613B:

| Поле | Изменение |
|---|---:|
| `processedCommandIds` | 2→502 ID;79→19579B; **+19500B** |
| `actors` | +105B, почти полностью в первом окне; количество actors остаётся2 |
| `revision`, `logicalClock`, `combatHistorySequence` | По+2B — дополнительные цифры счётчиков |
| `scene.round` | +2B |
| `attackActions`, `objects`, `concentrations`, `grapples`, `pendingResolution` | 0B |

Таким образом, устойчивый прирост — ровно **195B на ход** в списке ID уже
исполненных внутренних команд: пять ID по39B с JSON framing. У actor fields
`character` −6B, `runtime` +111B; passives, traits, masteryEffects, capabilities
не растут. После первого окна изменения actors ограничены несколькими байтами.
Признаков повторного накопления модификаторов или spatial-проекций здесь нет.
`attackActions` в этом сценарии пуст; его рост при множестве атак игрока этим
измерением не проверен.

Причина retention подтверждается кодом: `rules-core/reducer.ts:790` добавляет
ID при каждом `CommandCommitted`; `rules-core/handler.ts:344` проверяет его до
revision и отклоняет повтор как `DuplicateCommand`. Это сохранённый механизм
дедупликации, отдельный от API receipts и ограниченной видимой истории. Простое
обрезание массива изменит контракт повторов. Следующее улучшение требует
версированного checkpoint/retention решения и проверки поздних повторов/старых
readers; удалять ID или переписывать прошлые бои в этом срезе нельзя.

## Границы и воспроизведение

Локальный пробел «нет измерения длинной последовательности» закрыт для160
раундов этого сценария. Остаточный риск назван точно: **линейный рост внутреннего
dedup ID ledger и его повторная передача**, не доказанная утечка heap. Party6,
много summon/объектов, накопление attack ledger, многосуточный процесс и
production host budget не проверялись. Pool/delta ради этого замера не добавлены.

Output-only drivers: `outputs/testing/long-combat.mjs` и
`outputs/testing/long-combat-worker.mjs`; их hashes включены в JSON.
Запуск принимает `--source=<owned run directory>`,
`--artifact-hash=sha256:<pin>`, `--commands=160`; проверяет source registry и
создаёт свой стенд. Все созданные child handles, HTTP servers и PostgreSQL
очищаются независимо даже при ошибке; обе реальные registry имеют `stopped`.
Исходники приложения, тестов, инфраструктуры и общих scripts не редактировались.

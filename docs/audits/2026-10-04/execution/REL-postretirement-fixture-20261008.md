Production работает на 35a9bdf09e6f; успешная отдельная операция удаления V1/V2 и настоящий workflow записи 37693544430/1 подтверждают схему 308. Следующая конфигурация сборки добавляет только точную, уже установленную миграцию 302 из каноничного предложения `retirement-build-baseline`. Она не становится startup-миграцией и не выполняется повторно в рабочей БД.

Исправлены два препятствия последующим выпускам. Общая репетиция теперь проверяет реальные сохранённые identities каждого компонента предыдущей версии, включая раздельные выкатки. Публичный тестовый fixture готовит схему без V1/V2 через настоящий каноничный SQL только на принадлежащем runner изолированном стенде, после проверки пустых старых таблиц, полного snapshot/restore и неизменности прежнего журнала и сохраняемых строк. Проверка предыдущего приложения использует фактически установленный database baseline. Сравнение полного набора миграций остаётся строгим.

Тестовый helper не принимает DSN или сериализованное разрешение. Для него нужен созданный в текущем процессе owned adapter; наличие старых пользовательских строк, другой checksum или неизвестная запись удаления приводят к отказу. Его synthetic binding прямо обозначен подготовкой fixture и не служит разрешением production-операции. Приёмка рабочей БД по-прежнему требует отдельного полного V4 bundle.

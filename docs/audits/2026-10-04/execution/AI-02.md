## Результат

Все три зарегистрированных пути (`POST /api/images/generate`, `/api/images/generate-standalone`, `/api/cards/generate-image`) используют `generatedImageService`: локальная проверка конфигурации storage → один вызов provider → ограниченное получение raster bytes → object storage → подтверждённое обновление сущности, если оно нужно. Legacy endpoint сохраняет DTO `{image_url,message}`, современные endpoints — прежние поля ответа. Сервис больше не возвращает placeholder/data URL как успешный результат генерации. Существующие сохранённые data URL и исторические записи не изменялись.

Изменённые файлы:

- `backend/generated_image_service.go`: общий pipeline, interfaces для тестирования, безопасные типизированные ошибки, ограничение изображения 32 MiB, общий request budget 175 s, сохранение постоянной HTTP(S) ссылки и проверенного storage ID.
- `backend/image_controller.go`: адаптеры entity/standalone, проверка существования сущности до платного запроса даже при присланном `entity_data`, contextual Gorm update с `RowsAffected == 1`, единая запись `image_url` и `image_cloudinary_url`, поддержка token полей монстра. Удалены prompt/base64/entity-info logs и дублированные helpers генерации.
- `backend/controller.go`, `backend/main.go`: legacy CardController получает уже созданный ImageController, отдельный OpenAIService для Card больше не создаётся.
- `backend/openai_service.go`: provider и записываемая metadata используют один фактический model ID `gpt-image-1`.
- `backend/yandex_storage_service.go`: preflight проверяет наличие client/bucket локально; не требует нового `HeadBucket`/`ListBucket` permission. При неуспешном PutObject возвращается ID только вновь выделенного объекта для ограниченного cleanup.
- `frontend/src/api/imageErrors.ts`, `imagesApi.ts`, `client.ts`: совместимый optional AbortSignal, единый deadline 180 s для трёх callers, единые безопасные ошибки storage/persistence/transport, legacy route проходит через image error mapper. Автоматического повтора платного POST нет.

## Сохранность данных и исходы

| Сценарий | Поведение |
| --- | --- |
| Storage не настроен, entity отсутствует, отмена до provider | Provider не вызывается, `outcome=not_started`; старое изображение не изменяется. |
| Provider отказал | Его безопасный AI-01 error contract; без повторного вызова, upload и entity write. |
| Provider создал изображение, download/storage отказали | Ошибка с `outcome=not_saved`, без успеха/placeholder/data URL. Старое изображение не меняется. |
| Новое изображение загружено, отмена до UPDATE или UPDATE нашёл 0 строк | Удаляется только новый blob; cleanup получает отдельный context с лимитом 5 s. |
| UPDATE вернул transport/timeout/cancel или иной неопределённый исход | `image_persistence_unknown`, `outcome=unknown`; новый blob сохраняется, поскольку UPDATE мог успеть зафиксироваться. Пользователь получает просьбу проверить сохранённую сущность перед повтором. |
| UPDATE подтверждён, дополнительная metadata/library запись отказала | Основной результат остаётся успешным; blob остаётся; только безопасный diagnostic code. Metadata записывается отдельной транзакцией с request context и без вывода SQL parameters. |

Удаление прежнего изображения отсутствует во всём общем generation pipeline. При подтверждённом успехе лог содержит только request ID, model, размер изображения, provider latency и total latency. Prompt сохраняется в штатной entity/library metadata по прежнему контракту, но не выводится в stdout. Старые paid outcomes не переписываются.

## Ограничения и продолжение

- Preflight не доказывает сетевую доступность/права бакета: такая проверка вводила бы дополнительные permissions или тестовую запись. Реальная проверка provider/storage требует отдельного разрешённого внешнего прогона; здесь её нет.
- При неопределённом DB исходе возможен orphan blob. Его нельзя безопасно удалить внутри запроса; дальнейшая reconciliation/retention должна сопоставлять entity/library references и учитывать исходы. Старые blobs намеренно не удаляются.
- Metadata/library — вспомогательная транзакция после подтверждённого entity update; её отказ может оставить entity с корректной картинкой без новой записи в библиотеке. Добавлена безопасная диагностика, durable outbox/reconciliation пока отсутствует.
- Standalone по прежнему возвращает prompt и постоянный URL без entity/metadata записи в БД. Это существующий DTO/сценарий, не миграция старых данных.
- Изменения касаются генерации. Ручная загрузка/avatar/delete имеют отдельные исторические обработчики; их полный перевод на единый cancellation/uncertain-write contract не объявляется выполненным.
- AbortSignal поддерживается API callers; отдельная новая кнопка отмены или изменение существующих UI-flow не добавлялись.
- Неподдерживаемый `weapon_template`/временный ID теперь отклоняется до платного запроса. Прежний writer всё равно не умел сохранить такой результат; поддерживаемые entity types — card, monster, spell, action, effect, feat.

Откат: оставить adapters и безопасный отказ до provider, вернуть конкретную реализацию writer только после проверки её storage/DB исходов. Не возвращать placeholder/data URL fallback и не удалять blob при неизвестном commit outcome.

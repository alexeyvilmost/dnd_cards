## Нагрузка реальными командами

`node scripts/database/storage-growth.mjs` создаёт отдельный стенд для каждого объёма. Один fighter, 100/1000 настоящих camp_turn через API/worker/PostgreSQL, затем точный повтор каждого запроса, проверка сохранённого ответа, revision и исходного листа. В обоих прогонах PASS, cleanup завершён. Краткие отчёты сохранены в `execution/storage/growth-100.json` и `growth-1000.json`; полный bounded inventory и numeric samples — в указанных в них run directories под `outputs/testing/storage-growth/`.

Это физически выделенные PostgreSQL table/TOAST/index bytes, включая page granularity и мёртвые версии, а не размер полезного JSON. TOAST входит в table_bytes. p50/p95, response bytes, SQL и lock timing сохранены как диагностика: параллельные сборки создавали CPU contention. WAL — отдельный счётчик всего одноразового кластера с проверкой stats_reset; он не прибавляется к размеру БД. Процент экономии пока не заявлен. Результат подтверждает целесообразность DB-02 и DB-03 после их обязательных backup/replay dependencies.

## Дополнительные доказательства DB-02/03 и recovery

Новая серия DB-02: 1000 настоящих команд и 1000 exact retries, затем **эти же**
сохранённые JSON ответы записаны в отдельную legacy shadow с теми же индексами.
Это контролируемое сравнение representation, которому не нужно совпадение RNG
двух разных боёв. Legacy relation 44,507,136 B, compressed v2 26,492,928 B,
TOAST 44,023,808→25,968,640 B. Локальное уменьшение 40.47% подтверждено для
одинаковых ответов, не переносится на production и не утверждает ускорение API.
См. `DB-02-storage.json`/`DB-02.md`; исходные historical receipts не обновлялись.

DB-03: 30 новых боёв в каждом режиме; actual worker artifact одинаков. Legacy
frozen input имеет один distinct JSON, но хранится 30 раз: 2,350,470 logical B.
Новый формат — 30 references + один blob 78,359 logical B. Run+catalog physical
relations 4,784,128→2,834,432 B; это два synthetic прогона с разными UUID/RNG/time,
а не exact-state A/B. Init p95 182.7→194.0 ms на 30 samples не закрывает performance
acceptance; writer остаётся off. `DB-03-storage.json`/`DB-03.md`.

REL-06 сохраняет полный pending state, RNG cursor, envelope/catalog hashes,
receipts/journal и artifact A; restore на другом owned PostgreSQL и current B
продолжает оплачиваемое влияние ровно один раз. Повтор до/после принятия оставляет
сохранённые ответы и counters прежними. `REL-06-native-media.json` доказывает
непустой media inventory; `DB-02-recovery.json`, `DB-03-recovery.json` повторяют
путь с новыми storage formats и выключенными после restore writers.

Recovery доказывает сохранение закреплённого seed/состояния и идемпотентность,
**не** совпадение итогов двух независимых 1000-command seeded series. Последнее
остаётся открытым критерием, без искусственного утверждения fixed-RNG equivalence.
Все перечисленные стенды stopped. Dump size, relation bytes, WAL counters,
repository/context и каталог локального PostgreSQL не складываются в один размер.

Inventory расширен безопасными агрегатами `receipt_storage` (version/logical/
encoded bytes), frozen catalog payload и runtime JSON columns CharacterV3.
Data URL bounded metadata и индексные semantic preimages описаны в DB-04.

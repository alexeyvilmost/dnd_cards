# CLEAN-02: удалены устаревшие поколения персонажей V1/V2

По последующему прямому указанию владельца поддержка V1/V2 удалена из приложения; прежняя идея сохранять отдельный V2 export UI отменена этим указанием. Актуальный контур — `CharacterV3`, Forge и каноничный runtime. Файл `CharacterSheetV2.tsx` относится к текущему представлению V3 и сохранён вместе с его владельцем `CharacterSheetMVP.tsx`, бумажным листом, забегами, предметами и игровыми журналами.

Удалены два старых контроллера (1944 строки), их маршруты/конструкторы, модели/DTO, отдельные JSONB serializers старых владений/ресурсов/эффектов, V2 export backend и UI с тестами, неиспользуемый `charactersV2Api` и старые клиентские типы/redirects. Девять отдельностоящих Go-диагностик работали исключительно с V1 API и удалены; из архивных Python diagnostics убраны только старые character endpoints. Ручной `fix_foreign_key.sql`, возвращавший связь к V2, также удалён. Обязательный общий тест классификации оружия сохранён: теперь он проверяет тот же каноничный `default_attack_mode`, без удалённого V2 adapter.

Общие `Inventory`/`InventoryItem` сохранены для отдельных и групповых хранилищ. Удалены исключительно legacy связь с Character и запросы старого character inventory. Обнаруженный fallthrough неизвестного типа больше не позволяет обращаться к старым строкам через общий inventory API: допустимы `personal`/`group`, остальные дают404, не появляются в списке и не создаются. Старое снятие предметов по `inventories.character_id` удалено; текущая V3 экипировка использует собственный каноничный runtime и не изменена.

Проверка: компиляция backend PASS; actual PostgreSQL/Gin11/11 required tests, без skip, run `test_b254e5a79adae88d95241e5d`, cleanup=`stopped`. Новый тест проверяет обе неподдерживаемые разновидности, владельца/чужого пользователя, пять путей чтения/изменения, неизменность сохранённых строк, а также сохранённые личный/групповой контуры. Дополнительно прошли V3 JWT/revocation/ownership/atomic create/encounter ownership/delete serialization/templates и общий маршрутный контракт. Новый guard обязателен в core. Свежие TypeScript/Vite UI и worker13/13 прошли на `test_ab22e36eb0fbab752e2a1116`, cleanup=`stopped`; UI manifest `7857a429897a5f9c8138a03e815e0249a4312e0155aa53ba43a2e1fecf0f46d9`. Общие browser scenarios проверяются следующим полным набором.

## Физическое хранилище: отдельный контролируемый шаг

В этой правке не удалены таблицы и не изменена история миграций. Историческая цепочка переводила `inventories.character_id` с `characters` на `characters_v2`; реальная текущая схема может отличаться и требует inventory зависимостей. Нельзя применять `DROP ... CASCADE` по имени таблицы.

Читающая проверка production 05.10.2026 уточнила фактическую границу: в `characters` 21 строка, в `characters_v2` 12; общий размер этих таблиц с индексами — 671744 байта. Старый `character_id` заполнен у 10 хранилищ с 45 дочерними предметами; среди этих родителей нет используемых типов `personal` или `group`. Внешних ключей из других таблиц к двум старым таблицам и зависимых views не обнаружено; текущая схема не содержит старого FK `inventories.character_id`. Общая функция обновления времени и общие inventories/items должны сохраниться. [Метаданные проверки](CLEAN-02-production-dependencies.json) не содержат строк персонажей или персональных данных. Это предварительная инвентаризация, не подтверждение архива, удаления или возможности отката.

Экономия от удаления двух старых таблиц мала по сравнению с 1,809 ГБ квитанций команд. Поддержка V1/V2 уже убрана из приложения; физическое удаление выполняется после первого принятия V3-only версии, когда предыдущим проверенным приложением станет версия, которая больше не читает эти таблицы. До этого старые таблицы нужны для проверяемого отката действующего выпуска.

Следующий агент должен на owned восстановлении актуального backup:

1. Снять точные `pg_constraint`/trigger/view зависимости для `characters`, `characters_v2`, `inventories.character_id`; отдельно посчитать старые inventory parents и дочерние items. Не включать `characters_v3`, `character_events`, текущие owner grants, canonical sessions и roguelike runs в удаляемый набор.
2. Связать архив старых строк и зависимостей с manifest/hash исходного backup; выполнить restore и сверить row counts/полные данные. Не публиковать PII или содержимое архивов в отчёт.
3. Подготовить новую версионированную миграцию с проверяемым preimage и точным списком зависимостей; не переписывать прежние миграции, baseline fixture или receipt. Общие inventories/items остаются; удаляется только доказанный retired closure.
4. Проверить миграцию и восстановление backup на новом owned clone, затем текущие V3/paper/run/equipment scenarios. Такая операция не является additive298–300 и не может пройти через её backward-compatible approval.
5. Production-исполнение выполняет владелец релиза в рамках отдельного backup/cutover плана. Откат старого приложения требует сохранённых старых таблиц либо проверенного восстановления БД; эту границу нельзя скрыть переключением app image.

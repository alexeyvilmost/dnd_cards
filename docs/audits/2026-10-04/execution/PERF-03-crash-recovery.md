## Точные аварийные границы

Сценарий REL-06 создаёт реального персонажа через API, начинает бой, делает
каноничную атаку и доходит до сохранённого предложения влияния на бросок.
Выбирается действительно предложенное действие из каноничных деклараций.
В обеих фазах оно тратит `heroic_inspiration` 1→0 и продвигает сохранённый RNG.
Нового исполнения правил, подмены успешного ответа или production fault hooks нет.

| Граница kill | Что удерживает транспорт | Состояние после kill | Повтор той же команды |
|---|---|---|---|
| До commit | Полный настоящий HTTP200 от worker после вычисления, до передачи backend | Полный снимок run, character, receipts и связанных событий совпадает с исходным; receipt команды отсутствует | Полные worker input **и** result совпадают с удержанными; один commit и один расход |
| После commit | Настоящий HTTP200 API после независимого чтения durable receipt из PostgreSQL, до передачи клиенту | Полный снимок равен закоммиченному | Точный сохранённый ответ; 0 worker вызовов, 0 новых расходов/случайных значений |

Во всех случаях клиент первого запроса не получает ответа. Backend действительно
принудительно завершается через собственный `ChildProcess` handle и запускается
заново с теми же бинарником, БД и параметрами. Повтор сохраняет первоначальные
command ID, payload и expected revision. Revision забега 3→4 и runtime revision
персонажа 2→3 меняются ровно один раз; receipt 0→1. Дополнительный точный retry
не вызывает worker и не меняет полный снимок БД. Сравнение не удаляет игровые
поля, RNG, события, IDs или trace из результата.

Отдельная generation идентифицирует каждый запуск backend. Номер PID может
повторно использоваться ОС; разрешение остановки основано на собственном
живом `ChildProcess`, а не на поиске процесса по PID из файла.

## Guard и cleanup

`crash-recovery.test.mjs` проверяет реальные owned paths/registry, отказы на
escaped/stopped/mismatched source, изменение binary/artifact после копирования;
строгий verifier отклоняет потерю любой фазы, оплаты, продвижения RNG, equality,
source/execution binding или cleanup. Есть разрешённый reused-PID case и
запрещённые missing/repeated generation. Отдельный тест ломает остановку процесса,
proxy и БД одновременно и подтверждает попытку очистить **каждый** ресурс.

Все собственные backend generations, HTTP servers и PostgreSQL останавливаются
независимо в `finally`; ошибка одного cleanup не пропускает остальные и запрещает
PASS. В настоящем итоговом запуске все дочерние процессы завершились, registry
drill и отдельного CLI source имеют `stopped`, cleanup errors пуст.

Адресное воспроизведение: `node scripts/performance/crash-recovery.mjs`.
Оно создаёт актуальный локальный source stack без повторной UI сборки, выполняет
drill и очищает оба стенда. Общий extended runner переиспользует свой готовый
source stack через экспорт gate и создаёт только изолированный дочерний drill.

## Границы доказательства

Это crash **backend process** на двух точно наблюдаемых транспортных границах.
Проверка до commit останавливается после вычисления worker до передачи результата
backend; она не имитирует отключение PostgreSQL во время WAL/COMMIT. Проверка
после commit подтверждает durable receipt отдельным запросом прежде, чем убить
backend. Worker и PostgreSQL в этих фазах продолжают работать. Production,
отключение питания, убийство PostgreSQL и длинная боевая сессия здесь не проверялись.
Расширять архитектуру pool/delta ради этой проверки не понадобилось.

# Ускорение commands: снимок боя, компактный обмен и фоновое сохранение

На проде независимо подтверждён выпуск `011fd3801ad8`: бэкенд, фронтенд и
worker соответствуют опубликованным образам. Схема БД остаётся на версии 308.
**Предел 200 мс для всех команд пока не достигнут; 100 мс не объявляется SLA.**

Большой ответ движка содержал повторяющиеся состояние, каталоги и снимки
персонажей. Для точного сохранённого кадра следующий запрос теперь передаёт
около 2 КБ вместо 86 КБ, ответ движка — 67–181 КБ вместо примерно 1,8 МБ.
Бэкенд восстанавливает полный результат и проверяет исходный каноничный hash.
Иконки, различия отображения и чужие изменения листа не исчезают. Неизвестная
версия движка возвращается к полному протоколу до исполнения команды.

Повторный расчёт клеток существа объединён только внутри одного неизменного
пространственного наблюдения. Данные и сохранённые исполняемые артефакты
прежних боёв остаются исходными. Сравнение с оригинальным движком проверяет
полный результат, случайность и hashes истории. Браузер хранит четыре приватных
базы восстановления; изменение данных интерфейсом их не повреждает.

Настоящий запрос ждёт уже поставленный в очередь предварительный расчёт,
а новые догадки не вытесняют востребованную работу. Чтение неизменных действий
и эффектов происходит из снимка боя. Запись принятого результата идёт в фоне;
при аварии допустима потеря одной последней команды на забег. Следующая
команда сохраняет проверки владельца и ревизий. При штатном выключении сервер
ждёт сохранения. Повтор одного ID не бросает кубики и не списывает ресурсы вновь.

Замеры выполнены на отдельной копии боя на TimeWeb. Это внутренний HTTP
с восстановлением полного ответа на процессоре сервера; публичная сеть и
рендеринг настоящего браузера сюда не входят. По десять измерений каждой
обычной команды и по три в быстрой серии недостаточны для заявления SLA.

| Команда | Выпуск 30f9f605, медиана / максимум, мс | Выпуск 011fd380, медиана / максимум, мс |
|---|---:|---:|
| Завершение хода | 129 / 710 | 115 / 808 |
| Спасбросок, первая фаза | 108 / 136 | 115 / 154 |
| Спасбросок, вторая фаза | 100 / 147 | 87 / 138 |
| Спасбросок, третья фаза | 116 / 144 | 116 / 139 |
| Завершение хода в быстрой серии | 405 / 1550 | 377 / 1618 |

Исходный замер завершения хода до этих работ: медиана около 3071 мс.
Основной остаток задержки в быстрых сериях — вычисление непрогретого кадра
и конкуренция с сохранением предыдущей команды. Это требует следующей
измеряемой оптимизации; текущий выпуск не считается завершением этой цели.

На сервере оставлены две полные резервные копии: текущая перед выкаткой и
предыдущая. Более старая проверена и сохранена на ПК; удалён временный dump
завершённой репетиции. Дополнительно освобождено около 2 ГБ.

Выпуск `011fd380` использует ответ загрузки
боя как точную приватную базу первой команды. Токены `read:UUID` отделены от
ID команд; чтение не создаёт квитанции и не изменяет принятую ревизию.
В изолированной локальной проверке размер загрузки уменьшился с 4,36 до
1,83 МБ, первого ответа — с 1,86 до 0,49 МБ. Эти локальные результаты не
объявляются измерением TimeWeb. Выкатка 37789730292 и независимая проверка
точных опубликованных образов завершились успешно.

Допуск пользователя расширен до потери последнего хода. Сейчас реализация
по-прежнему ограничивает потери одной несохранённой командой: полноценный
буфер активного хода ещё не внедрён. Он должен хранить квитанции всех принятых
команд, сохранять их порядок и проверку владения, а завершение боя и операции
с экономикой должны ждать надёжной записи.

На изолированном TimeWeb стенде LZ4 для двух JSON-колонок снизил медианы
быстрых спасбросков до 254–275 мс. Совместный эксперимент с кэшем маршрутов
и прогревом worker дал 204–230 мс; максимум был 371–423 мс. Это экспериментальные
результаты, изменения ещё не выкатаны, и предел 200 мс ими не подтверждён.
Кэш маршрутов подготовлен в отдельной ветке; сборка worker прошла 49 тестов. Он действует
только внутри одного неизменного расчёта: следующий расчёт заново наблюдает
изменённые эффекты, позиции и состояние участников.

Следующий локальный пакет также включает LZ4 для новых соединений приложения,
прогрев точного кадра при загрузке боя и отдельные измерения записи каждой
таблицы. Изменение схемы не требуется. Повторное использование компрессора
квитанций сохраняет прежние gzip-байты и уменьшает выделения памяти примерно
на 1,2 МБ на запись. Проверка параллельных независимых квитанций прошла.
35 выбранных Go-проверок, включая атомарность, повтор и сбой фонового сохранения,
прошли. Это локальные проверки, пакет ещё не выкатан.
Те же 35 проверок прошли с детектором гонок Go на Windows и отдельной БД;
это дополнительная проверка, обязательный Linux CI остаётся частью выкатки.

Сжатие неизменной принятой квитанции теперь выполняется одновременно с SQL
записью и обязательно завершается до её вставки. Ошибка по-прежнему откатывает
всю транзакцию. В локальной быстрой серии средняя транзакция сократилась
со 139 до 89 мс, ожидание предыдущего сохранения — с 68 до 22 мс. Медианы
завершения хода и последнего спасброска составили 74 и 48 мс. Непрогретое
приближение занимало 240–265 мс, максимум завершения хода — 496 мс.
Три измерения каждой фазы на ПК не подтверждают предел 200 мс на TimeWeb.

Чтение настроек TimeWeb 8 октября подтвердило два доступных CPU и около 4 ГБ
памяти. У backend и worker нет ограничений Docker по CPU; счётчики CPU throttling
равны нулю, OOM не отмечен. Нагрузка снята во время другой выкатки и не является
замером обычного трафика. Фоновая запись и предварительный расчёт делят эти
два CPU; их конкуренцию нужно измерять на фактически развёрнутых образах.

Эксперимент с восстановлением неизменных частей JSON через SQL исключён:
средняя запись забега увеличилась примерно с 29–33 до 162 мс. Флаг V8
`--no-lazy` также не добавлен: измеримого выигрыша не установлено.

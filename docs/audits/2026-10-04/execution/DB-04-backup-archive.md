# Компактное хранение закрытых резервных копий

07.10.2026 локально проверены три ранее сохранённые копии production dump от
29.09.2026. Общие блоки позволили упаковать 2 257 172 120 байт в 776 803 113 байт
вместе с manifest. Потенциальная экономия — 1 480 369 007 байт, или 65,59%.
Каждый файл полностью восстановлен в новый каталог и независимо проверен
по размеру и исходному SHA-256; исходники после чтения также перепроверены.

Добавлены `scripts/database/backup-archive.mjs`, versioned reader,
pack/verify/restore и обязательные тесты в основном наборе. Один набор содержит
явно выбранные закрытые файлы с уникальными именами. Прерывание чтения,
изменение исходника, отсутствующий/повреждённый блок, неподдерживаемый формат,
выход имени за каталог и linked paths приводят к отказу. Запись требует нового
каталога, исходники не удаляются, восстановление создаёт только файлы.

Проверки: 11/11 Windows, 11/11 Linux в локальном Docker без сети и 41/41 проверки
manifest/sharding; обязательных пропусков нет. Проверка изменений на известные
секреты и незапрошенную регистрацию прошла. Pack, restore и независимая сверка
трёх реальных копий заняли 72,3 секунды на локальном компьютере.

Это локальная подготовка DB-04. На сервере исходные backup сохранены; архивами
они не заменялись. Фактически освобождённое этим изменением место на сервере —
0 байт. Проверено восстановление точных файлов, без отдельного запуска
`pg_restore` в этом измерении. Результат трёх похожих старых копий не обещает
такую же экономию для всех snapshots. Последняя копия, активное восстановление,
исполняемые правила, media и остальные части полного capture требуют прежнего
сохранения. Автоматического retention, TTL или удаления пользовательских данных
нет. Исходные критерии всех 29 задач плана сохранены; весь план не объявляется
выполненным.

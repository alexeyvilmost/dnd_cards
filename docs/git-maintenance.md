# Измерение Git и безопасная очистка

Инструмент `scripts/maintenance/media-inventory.mjs` только читает рабочие
файлы и Git, записывая новые отчёты. Он не выполняет `gc`, `prune`, `clean`,
`filter-repo`, staging или переписывание истории. Неиспользуемость файла нельзя
устанавливать только по отсутствию текстовой ссылки.

```powershell
node scripts/maintenance/media-inventory.mjs --manifest NEW_MANIFEST.json --summary NEW_SUMMARY.json
node scripts/maintenance/media-inventory.mjs --verify EXISTING_MANIFEST.json
```

Проверка 04.10.2026:

| Локальный dist | 169 174 309 байт, 628 файлов | Снимок локальной сборки до variants; не production |

| loose objects | 527 621 KiB, 4074 объекта | Локальное хранилище; не размер checkout |
| garbage | 156 245 KiB, 29 файлов | Не удалялись |

`git fsck --full --no-reflogs --no-progress` завершился с кодом 0; 1241 строка
о dangling объектах. Это не означает, что их можно удалить: они могут содержать
восстанавливаемую историю. Сначала следует раздельно сохранить refs, reflog и
неопубликованную работу, а затем принимать решение о локальном обслуживании.
Размеры `.local-postgres`, outputs, backups и Git — разные категории; ни одна
из них не подменяет измерение production БД.

Найдено только 3492 повторных байта в точных дублях публичных gallery.js/css.
Удаление этих файлов не даёт существенного эффекта, но способно сломать старые
URL. Основной объём: карты 59,6 МБ, аудио 60,9 МБ, PNG всего 90,5 МБ. Для
доставки кода полезнее уже реализованный отдельный Docker-слой public и сборка
по закрытому набору входов. Фактический reuse слоя пока не измерен: Docker
daemon недоступен в этой среде.

Возможные дальнейшие действия, каждое с отдельной проверкой:

1. После сохранения локальной неопубликованной истории оценить обычный Git GC;
   не использовать агрессивный prune как автоматическую часть выпуска.
2. Для исторических больших бинарников рассмотреть LFS или внешнее immutable
   хранилище новых версий. Сначала подготовить инвентарь всех refs/потребителей,
   полную резервную копию и способ получения файлов из чистого clone. Само
   включение LFS не сокращает уже существующую историю.
3. Переписывание опубликованной истории требует отдельного запроса владельца
   и согласованного перехода всех копий/CI. Оно не выполнялось.
4. Новые медиа готовить как версии с SHA-256 и provenance; старые URL сохранять.
   Инструкции и измеренная конверсия — [media-storage.md](media-storage.md).
5. Не включать outputs, backups, tmp, `.local-postgres`, node_modules и `.git`
   в контекст вручную запущенной сборки. Git archive и локальный Docker context
   имеют разные границы; REL-02 проверяет оба вида входов отдельно.

Документация Git: [fsck](https://git-scm.com/docs/git-fsck),
[gc и ограничения очистки](https://git-scm.com/docs/git-gc).

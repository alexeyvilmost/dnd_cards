# Автоматическая выкатка проверенного коммита

Путь доставки: `main push → CI → immutable images → свежий backup → репетиция на копии БД → замена затронутых сервисов`. На 06.10.2026 версия `93265633` прошла полный CI15, публикацию и реальную выкатку на TimeWeb; независимая проверка подтвердила компоненты и 305 записей миграций. Автоматическая и раздельная доставка следующего пакета ещё требуют реальных проверок, внешние переключатели остаются выключены. [Точная запись](audits/2026-10-04/execution/CI-15-healthy-adoption.md).

## Как выбирается версия

`ci.yml` проверяет каждый push в main расширенным набором. PR выбирает набор по изменениям. Коммит приложения берётся из успешного CI, а коммит скриптов управления — из текущего main workflow; это отдельные поля. Автоматическая сборка и выкатка отклоняют кандидата, если main уже ушёл вперёд. Уже начавшееся переключение не отменяется новым push.

Последняя выкатка определяется по завершению действительно выполненного `deploy` job, включая повтор старого workflow. Зелёный запуск с пропущенным job не считается выпуском. Отсутствующий или истёкший receipt последней фактической выкатки блокирует процесс; более старый receipt не подставляется. Ограничение полноты API и процедура описаны в [отчёте discovery](audits/2026-10-04/execution/REL-baseline-discovery.md).

Сравнение идёт с последним выкаченным manifest. Совпадающие fingerprints сохраняют прежние frontend/backend/worker digests. Изменения общих правил выбирают всех потребителей. Неизвестная зависимость приводит к полному набору. Контейнеры собираются вне production; на сервере используются готовые digest-образы.

## Что потребуется при включении

В `infra/release-build-config.json` проверяются immutable pins инструментов и базовых образов, content manifest и migration identity. Проверенный tracked config и внешние разрешения GitHub — отдельные условия. Репозиторий использует следующие независимые переключатели:

| Настройка | Назначение |
|---|---|
| `RELEASE_BUILD_ENABLED` | Разрешает сборку проверенных образов |
| `AUTO_RELEASE_MAIN_ENABLED` | Разрешает запуск сборки после успешного main CI |
| `RELEASE_PUBLICATION_ENABLED` | Разрешает публикацию проверенных образов |
| `PRODUCTION_DEPLOY_ENABLED` | Разрешает protected production job |
| `AUTO_DEPLOY_MAIN_ENABLED` | Разрешает автоматическую выкатку опубликованного кандидата |
| `AUTO_RECONCILE_MAIN_ENABLED` | По умолчанию `false` (отсутствующая variable также выключает). После успешной фактической выкатки разрешает одну новую полную CI-проверку последнего main, если он ушёл вперёд. Требует всех пяти разрешений выше и tracked `autoDeployMain:true`. |
| `DEPLOY_HOST_CONFIG_FILE` | Абсолютный путь к проверенной конфигурации trusted host |
| `REHEARSAL_CONFIG_FILE` | Абсолютный путь к шаблону конфигурации репетиции |

Дополнительно проверяется tracked policy `infra/deployment-policy.json`. Переменная GitHub не обходит выключенную policy. Protected job выполняется на GitHub-hosted runner и передаёт точные проверенные файлы по SSH с закреплённым host key. Production-секреты доступны только окружению `production`; PR jobs не получают доступ к серверу.

Первое восстановление после подтверждённого отказа до переключения допускается только через явный `first_adoption_recovery` и проверенный файл из текущего control commit. Даже при включённом selective planning оно требует полной extended-проверки и сборки всех трёх образов. Failed run не становится successful baseline; перед capture и под lock повторяются проверки main, истории попыток и прежнего состояния. Обычный автоматический путь не подставляет это исключение.

## Backup и репетиция

Сохранённый host config использует `backupDirectory = <root>/backups`. Этот каталог должен существовать вне рабочего каталога GitHub runner. Для каждой попытки создаётся новый `capture-<run ID>-<attempt>`. Snapshot и боевые artifacts имеют приватные права и не загружаются в GitHub artifacts. Неуспешные частичные копии сохраняются для диагностики.

`prepare-host-release.mjs` вызывает read-only capture, связанный с фактическими образом, здоровьем и DATABASE_URL работающего backend. Пароль не попадает в аргументы процесса или отчёт. Затем создаются приватные конфигурации конкретной попытки: репетиция читает `captureDirectory`, выкатка — ту же копию через `backupDirectory`. Исходный host config не переписывается.

Capture сам по себе не считается проверенным backup. PostgreSQL восстанавливается в отдельную БД; только из неё берутся schema, ссылки на artifacts и media. Продолжение сохранённого выбора, повтор команды и запуск точных образов проверяются перед созданием итогового bundle. Провал проверки или cleanup не создаёт разрешение на выкатку. Перед переключением повторно проверяются активный predecessor и ссылки на боевые artifacts.

Backup содержит БД, исполняемые artifacts и ссылки на медиа. Наличие байтов внешних объектов в Cloudinary/S3 требует отдельной политики хранения. Новые файлы backup автоматически не удаляются; обслуживание retention отделено от выкатки.

Подробности миграций, журналирования и отката — в [release-deployment.md](release-deployment.md). Первичное перенесение существующего legacy-развёртывания в проверенный manifest остаётся отдельной операцией: старые digests и checksums нельзя восстановить предположением.

## Последовательные push и устаревшая подготовка

Перед запуском host job автоматический deploy повторно читает manifest последней фактической успешной выкатки. Если опубликованный кандидат опирается на прежний predecessor или main уже изменился, prepare записывает `superseded`, а job `deploy` пропускается. Такой запуск не является неудачной попыткой переключения. Неизвестные, неуспешные фактические host attempts по-прежнему требуют ручного разбора; сохранённые кандидаты и receipts не переписываются.

Опциональный `reconcile.yml` проверяет завершённую фактическую выкатку и при необходимости запрашивает свежий `ci.yml` с `suite=extended` на текущем main. Полная проверка проходит обычный release/deploy путь. Подтверждение попытки сохраняется до единственного POST. Это ограниченное согласование, а не гарантия доставки: потерянный запрос, неизвестный ответ, отмена или сбой не повторяются автоматически. Ограничения, включение и безопасное ручное восстановление описаны в [release-reconciliation.md](release-reconciliation.md). Реальное выполнение новой цепочки GitHub Actions должно быть принято отдельно; локальные контрактные тесты его не заменяют.

# Публичный режим и эксплуатационные ограничения

Состояние на 2026-08-05. Публичными остаются чтение глобальных каталогов и
отдельные legacy-прототипные routes. Они могут использовать общего пользователя
`public` и не являются границей изоляции данных.

Контур `CharacterV3` (`/api/characters-v3/**`) и онлайн-бои являются исключением:
все их routes требуют валидный Bearer JWT через `StrictAuthMiddleware`.
Отсутствующий, повреждённый или просроченный JWT получает `401` и никогда не
подменяется общим пользователем.

На миграционный период действует следующая политика листов:

- пользователь создаёт листы только на свой `user_id`;
- список и GET показывают собственные листы и исторические листы владельца
  `public`;
- каждый ответ CharacterV3 явно содержит `access_mode: owner` либо
  `access_mode: legacy_public_readonly`; UI не выводит право записи из имени
  пользователя или UUID;
- исторические `public`-листы и их журналы доступны авторизованным пользователям
  только для чтения;
- PUT, DELETE, PATCH runtime и POST событий разрешены только владельцу;
- чужой приватный лист не попадает в список, а прямой доступ получает `403`;
- существующие `public`-записи не переназначаются автоматически. Их будущая
  передача аккаунтам требует отдельной подтверждаемой миграции.

Начальные runtime-поля (экипировка, инвентарь, ресурсы, активные эффекты,
состояние хода и валюта) принимаются в POST CharacterV3 и записываются тем же
INSERT. Клиенты не должны создавать лист, а затем инициализировать его вторым
PATCH: такой двухшаговый протокол оставлял частичные строки и дубликаты при
сетевой ошибке.

Текущая граница листа — single-writer: отдельные PATCH runtime и POST журнала не
имеют общей revision/CAS-транзакции, а действие одного автономного листа над
другим не является одной серверной командой. UI не должен заявлять такую
последовательность атомарной. Для совместного боя более сильной границей
является транзакционный `/api/encounters/:id/apply`; проектирование единой
идемпотентной character-command с revision остаётся отдельным этапом.

Backend применяет:

- request ID и безопасные HTTP-заголовки ко всем ответам;
- лимит JSON-body 2 MiB и multipart upload 12 MiB;
- общий лимит мутаций 180 запросов в минуту на IP и endpoint;
- отдельные лимиты регистрации, входа, AI-механик, генерации и загрузки
  изображений;
- audit-log мутаций без тела запроса;
- batch журнала не более 200 событий и идемпотентность по
  `(character_id, client_event_id)`.

Лимитеры хранятся в памяти процесса. При горизонтальном масштабировании их надо
заменить общим хранилищем (например, Redis), иначе каждый инстанс будет считать
окно независимо.

`npm audit` после обновления зависимостей оставляет два high-advisory в
React Router, относящихся к RSC/server actions. Текущий frontend — клиентский
Vite SPA и эти режимы не использует; исключение контекстное и должно быть
перепроверено при появлении безопасной версии или внедрении SSR/RSC.

Удаление production-данных запрещено без отдельного подтверждения. Старые V1/V2
модели и SQL-дампы считаются кандидатами на удаление, но пока сохраняются из-за
неполной доказанности отсутствия внешних потребителей.

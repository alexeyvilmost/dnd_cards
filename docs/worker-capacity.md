# Ограничения нагрузки движка правил

Два независимых ограничения включены по умолчанию. Они не меняют правила,
идентификаторы команд, RNG, закреплённые версии или порядок транзакций.

| Настройка | По умолчанию | Допустимый диапазон | Граница |
|---|---:|---:|---|
| `RULES_WORKER_MAX_INFLIGHT` | 4 | 1–64 | Все обращения одного процесса backend к worker: до JSON marshal, HTTP и до окончания проверки ответа |
| `RULES_WORKER_MAX_CACHED_ARTIFACTS` | 4 | 1–64 | Число сохраняемых worker-ом загруженных CJS-модулей в LRU |

Backend использует один общий ограничитель, даже когда контроллер создаёт новый
client. Очереди ожидания нет: пятый запрос получает фиксированный
`combat_worker_busy` и текст «Сервис правил занят. Действие не применено;
повторите попытку». API сохраняет существующее отображение worker-отказа в HTTP409.
До worker запрос не доходит. Ошибка не создаёт квитанцию и не меняет сохранённые
ресурсы/случайность. Повтор должен сохранить прежние command ID и payload;
принятая ранее команда возвращает свою квитанцию без обращения к worker даже
при заполненном лимите. Автоматического повтора с новым ID нет.

Отменённый context проверяется до admission и после сериализации; отмена во
время HTTP освобождает локальное разрешение. Она не может остановить уже начатый
синхронный JavaScript в удалённом процессе. Поэтому предел относится к активным
Go-вызовам, а не к уже отменённым HTTP-запросам, TCP backlog, другим backend
репликам или прямым внутренним клиентам worker. Worker остаётся внутренним
аутентифицированным сервисом. При добавлении backend реплик общий бюджет нужно
распределить; запуск четырёх реплик не сохраняет общий предел4.

LRU освобождает собственную ссылку, Node `require.cache` и ссылку из parent module.
Архивные файлы не удаляются. Повторное обращение к вытесненной версии читает
сохранённый файл, заново проверяет SHA-256 и загружает ту же версию. Отсутствующий
или повреждённый файл не подменяется текущим артефактом. Выполняющийся запрос
сохраняет свою ссылку до конца исполнения. На остановке wrapper очищает свои
module references. Это предел живых сохранённых модулей, **не общий лимит heap**:
на Node24 память V8 после11 разных артефактов почти не снизилась даже после GC.
RSS не обязан уменьшаться; pool/VM и автоматический restart здесь не добавлены.

Неверное значение backend приводит к безопасному `combat_worker_unconfigured`
до сериализации. Неверное значение cache не позволяет запустить wrapper.
Ноль не означает «без ограничений». Mirrors и остальные rollout flags не
включаются этими настройками.

Для локального процесса можно задать обе переменные окружения, например:

```dotenv
RULES_WORKER_MAX_INFLIGHT=4
RULES_WORKER_MAX_CACHED_ARTIFACTS=4
```

`infra/compose.prod.yml` передаёт их через Compose interpolation с теми же
defaults. Значения задаются в окружении **процесса Compose** или его `.env` /
`--env-file`; это отличается от service `env_file`. Менять production параметры
можно только в отдельно разрешённом release. Повышение лимитов требует нового
профиля фактического host budget; приведённые числа не являются TimeWeb SLA.

Локальные проверки: `scripts/performance/check-worker-admission.mjs` — реальный
HTTP и owned PostgreSQL; `profile-worker.mjs --mirrors --capacity` — отдельные
fresh processes, истинный cold и1/4/16 запросов; `retained-artifacts.mjs --compare`
— одинаковые существующие owned исторические CJS в двух свежих процессах с
лимитами64 и4. Forced GC применяется только в диагностическом child. States,
семена и токены не записываются в отчёт.

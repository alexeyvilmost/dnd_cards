# Публичные изображения и варианты без потери пикселей

По умолчанию приложение использует прежние URL. Локальный конвейер создаёт
дополнительные полноразмерные WebP, не меняя PNG, данные сущностей, сохранённые
листы, боевые снимки или старые ссылки. Пока преобразование подключено только к
фону `TacticalBattleMap`; остальные изображения не подменяются автоматически.

## Проверенный контракт

`scripts/maintenance/build-media-variants.mjs` принимает только неподвижные
8-битные PNG в sRGB либо с сохраняемым побайтно ICC. Изображения с нестандартными
gAMA/cHRM, HDR, EXIF/orientation, анимацией и неподдержанной глубиной остаются
оригиналами. Вариант должен быть меньше оригинала. Размеры не меняются.

Кодек закреплён: Sharp 0.35.4, libwebp 1.6.0; параметры
`{lossless:true,exact:true,effort:6}`. После кодирования оба файла заново
декодируются в полный RGBA, включая цвет полностью прозрачных пикселей.
Проверяются равенство всех байтов, размеров и ICC. SHA-256 исходника,
варианта, RGBA, ICC и версии библиотек записываются в манифест. Кодек не является
зависимостью обычной сборки. Для включения конверсии в CI нужна отдельно
закреплённая зависимость, а не абсолютный путь локального компьютера.

Дополнительное правило — **только непрозрачная или бинарная альфа (0/255)**.
Первый эксперимент дал 93 варианта с полным совпадением RGBA в Sharp, но Chrome
отобразил иначе 70 из них. Все различия были в RGB частично прозрачных пикселей;
непрозрачные пиксели и значения альфа совпали. Это согласуется с различным
округлением при premultiply/unpremultiply, но внутренний код браузера здесь не
исследовался. Исключена вся группа из 76 изображений с частичной альфой, включая
шесть случайно совпавших. Это свойство входных данных, а не перечень удачных
файлов. После полного повторного прохода 17/17 вариантов совпали в Chrome.

## Локальное воспроизведение

Все выходные каталоги и отчёты должны быть новыми. Скрипты не перезаписывают
существующие результаты. Пример из корня репозитория:

```powershell
node scripts/maintenance/build-media-variants.mjs --output outputs/maintenance/NEW_BUNDLE --sharp-module ABSOLUTE_SHARP_MODULE
node scripts/maintenance/check-media-encoder.mjs ABSOLUTE_SHARP_MODULE
node scripts/maintenance/check-media-browser.mjs outputs/maintenance/NEW_BUNDLE outputs/maintenance/NEW_BROWSER_REPORT.json
```

`ABSOLUTE_SHARP_MODULE` — явно предоставленная локальная установка нужной
версии. Путь не записывается в клиентский код. Браузерная проверка использует
изолированный локальный HTTP-сервер, Chromium/Chrome и реальные изображения;
внешние запросы запрещены. Она сравнивает canvas RGBA всех выбранных пар.
Это проверка декодирования, а не пользовательских сценариев или времени загрузки.

Сборка с вариантами требует переменных процесса `VITE_MEDIA_VARIANTS=1` и
`MEDIA_VARIANTS_BUNDLE=ABSOLUTE_BUNDLE_DIRECTORY`. При выключенном флаге сборка
не читает этот каталог и не требует кодека. `frontend/scripts/media-variants.mjs`
перед сборкой проверяет полноту списка PNG, хеши всех исходников/вариантов,
размеры, ICC/альфа-контракт и безопасные пути; ошибки останавливают сборку.
Rollup-плагин добавляет файлы в `dist/media/variants/<sha256>.webp`, не записывая
их в исходный `public`. Vite встраивает только проверенный URL-манифест.

Старый кандидат с частичной альфой намеренно не проходит адаптер сборки.
Диагностический режим `--inspect-legacy-candidate` браузерного инструмента
разрешает исследовать старый отчёт, но адаптер в этом режиме не выдаёт ни
runtime-манифеста, ни плагина эмиссии файлов.

## Runtime, кеш и откат

`mediaVariants.ts` проверяет и замораживает независимую копию манифеста.
Подмена разрешена только для точного локального PNG URL из него. Неизвестные,
внешние, `data:`, `blob:`, URL с query/hash остаются исходными. Невалидный
манифест возвращает все оригиналы. Режимы resolver `print`/`export` возвращают
исходный URL; существующие API печати/экспорта не изменены.

В HTTP-конфигурации SHA-256 WebP имеют immutable URL. Старые файлы сохраняются
для уже открытых вкладок. `scripts/release/retained-assets.mjs` переносит только
пути, соответствующие immutable-маршрутам: Vite `assets/<name>-<hash8>.<ext>`,
`workbox-<hex>.js`, `media/variants/<sha64>.webp`. Для последнего проверяется
содержимое против имени. При коллизии имени с другими байтами выпуск
останавливается; ранее сохранённые файлы не удаляются. HTML, `sw.js`, unhashed
авторские assets не добавляются в этот архив. Реальная Docker/TimeWeb проверка
архива остаётся отдельным условием перед выпуском.

Откат — выключить флаг и пересобрать фронтенд с оригинальными URL. Варианты для
старых вкладок сохраняются. Прямые ссылки и исходные PNG доступны до и после
отката. При потере отдельного файла на сервере CSS background сам не переключится
на оригинал: целостность всех вариантов проверяется сборкой, а HTTP-проверка
должна быть выполнена перед выпуском. Не включать флаг до этого условия.

## Результат и оставшиеся условия

Проверено 135 PNG общим размером 90 524 494 байта. После строгих фильтров:

| Группа | Вариантов | Исходники, байт | WebP, байт | Разница |
| --- | ---: | ---: | ---: | ---: |
| Все допустимые | 17 | 42 818 912 | 29 448 348 | −13 370 564 (31,23%) |
| Карты/фоны | 11 | 35 277 787 | 24 557 492 | −10 720 295 (30,39%) |

Эти числа — размеры файлов. Пользователь не загружает все карты одновременно.
Пока resolver используется только для фона карты; экономия остальных вариантов
ещё не реализована на экранах. При сохранении оригиналов размер Git не уменьшается,
а включённый дистрибутив получает дополнительные 29,4 МБ. Снижение возможного
трафика нельзя называть снижением размера репозитория или Docker-образа.

Список 308 исходных файлов (`public` и `references`) с хешами и найденными
литеральными ссылками — `CLEAN-03-media-manifest.json`; отсутствие найденной
ссылки не доказывает неиспользование: есть динамические URL, БД и история.
Полные результаты — `docs/audits/2026-10-04/execution/CLEAN-03-*`.

Остаются отдельные условия: включённая сборка и UI-сценарий (отчёт корневого
агента), визуальная проверка на нескольких браузерах/плотностях, печать/экспорт,
HTTP-доступность оригиналов и вариантов после выкладки, OCI cache/size checks.
Для enabled OCI сборки bundle и флаг должны стать явными входами новой версии
release fingerprint/context. Сейчас release schema v1 и frontend Dockerfile
явно отклоняют enabled/bundle, а не молча собирают другое содержимое.
До этого флаг остаётся выключенным. Аудио, SVG, JPEG, оригиналы из `references`
не преобразовывались. Права/лицензии неизвестных оригиналов не переопределялись;
профили и преобразования связаны с исходным SHA, оригинальные метаданные остаются
в исходном файле.

Спецификации: [WebP lossless и exact](https://developers.google.com/speed/webp/docs/cwebp),
[Sharp output/ICC/raw](https://sharp.pixelplumbing.com/api-output/).

## Граница OCI и подготовка входов

Текущий config принимает только `frontendMediaVariants:false` (отсутствие поля
также означает false). Неизвестные поля блокируются. В fingerprint и build args
фронтенда включено `VITE_MEDIA_VARIANTS:'0'`. Попытка передать `1` или внешний
`MEDIA_VARIANTS_BUNDLE` останавливается в plan, CI image CLI, Docker build guard
и генераторе baked frontend identity. Нельзя получить формально верный image
identity для неучтённых файлов. Исторические manifests не переписываются;
новый fingerprint может потребовать rebuild вместо reuse прежнего frontend.

Локальная enabled UI сборка остаётся доступна для испытаний. Она не становится
OCI-кандидатом и не доказывает готовность выпуска. Отдельный инструмент готовит
доставляемый набор файлов с точным digest, без Docker и сети:

```powershell
node scripts/release/media-build-inputs.mjs --bundle outputs/maintenance/VERIFIED_BUNDLE --browser-report outputs/maintenance/PASSING_REPORT.json --output outputs/maintenance/NEW_OCI_INPUT
```

Инструмент заново проверяет оригиналы/варианты/eligibility, требует полный
успешный browser report именно по этому набору URL, копирует только
перечисленные WebP и manifest в новый `bundle/`, сохраняет browser proof и
`media-input.json`. Вне манифеста файлы не читаются/не передаются. Record содержит
SHA-256 каждого файла, точных bytes manifest, canonical file-list fingerprint
и runtime mapping. Browser evidence привязано ретроспективным совпадением URL и
хешей; это не подписанная аттестация CI. Набор помечен
`prepared_not_release_authorized`, `deployable:false`; его fingerprint не
называется OCI digest или component input fingerprint.

Для текущего v2 подготовлены 18 файлов, 29 507 508 байт. Bundle fingerprint:
`sha256:b7c9a812753d56f8c0aac28dc43047f127784f5a052f8eb07867d9b7fbec590f`.
Точный manifest hash:
`sha256:e4a16d54d1cf6fbd2d7f7b60a1b83eb45c091c0e82d3163d3da39f71788f26ec`.
Это локальное содержимое `outputs/maintenance/media-oci-input-20261004-v2`;
копия record — `docs/audits/2026-10-04/execution/CLEAN-03-oci-media-inputs.json`.

Перед разрешением enabled OCI требуется явное расширение manifest/config:

1. Указать обязательные `mediaBundleFingerprint`, manifest/blob/browser proof
   digests и encoder/eligibility version в config и fingerprint frontend.
   Изменение только bundle должно выбирать rebuild frontend, даже без Git diff.
2. Подать проверенный `bundle/` как отдельный named BuildKit context; сверять
   closure/digests перед сборкой и после получения image. Никаких ambient
   каталогов outputs или неучтённых network downloads.
3. Сделать все original PNG доступными build adapter. Нынешняя Docker compile
   stage содержит только DiceBox/PWA inputs: обычного COPY bundle недостаточно.
   Media-only изменение не должно скрыто обходить validation layer.
4. Встроить matching manifest, получить настоящие OCI digest/image identity,
   проверить старые/new URLs, print/E2E, retained WebP после rollback и доступ
   из ранее открытой вкладки. Измерить cold/warm layers на Docker host.
5. Только после этих проверок отдельно включать release/publication/deploy.

Этот этап не выполнялся: Docker daemon недоступен, публикация/production не
запрашивались. Fail-closed guard является текущим принятым ограничением.

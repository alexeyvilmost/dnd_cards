# Кросс-связи библиотеки

Связь — прямое обращение к другой сущности из данных механики. Описания, Markdown,
ссылки `[[...]]`, заголовки и служебные данные проверки не создают связи.
Обратная связь вычисляется из того же ребра: независимо редактируемого второго
списка нет. Цепочка «класс → действие → эффект» содержит две прямые связи.

## Контракт API

Ответы каталога содержат `references` (используемые сущности) и `referenced_by`
(использующие эту сущность). Пустое значение — `[]`.

```json
{
  "references": [],
  "referenced_by": [
    {
      "entity_type": "class",
      "entity_id": "uuid-класса",
      "name": "Название класса",
      "level": 3,
      "paths": ["level_progression.3.effects[0]"]
    }
  ]
}
```

`entity_type` — тип библиотечной сущности, `entity_id` — её канонический ID.
`level` присутствует у явно привязанных к уровню выдач класса или вида
(`level_progression`, `min_level`, рост ресурса) и относится к уровню источника,
а не к уровню заклинания. Обычная связь без привязки не получает выдуманный
первый уровень; это уточняет миграция `283_explicit_reference_levels`.
Несколько выдач одной сущности на разных уровнях
сохраняются отдельно. `paths` объясняет, какие поля создали связь. Ссылка на
отсутствующую цель помечается `missing: true` и сохраняет исходный идентификатор.

- `GET /api/entity-references/:type/:id` — актуальные связи сохранённой сущности.
- `POST /api/entity-references/:type/preview` с телом `{"entity": {...}}` —
  расчёт связей черновика без сохранения механики.
- `POST /api/entity-references/:type/:id/refresh` — повторный расчёт сохранённой
  сущности с проверкой прав редактирования.
- Обычные `POST`, `PUT`, `PATCH` и `DELETE` сущностей обновляют индекс через
  транзакционные триггеры БД. Для изменения связи меняется её исходное поле
  механики в обычном запросе редактора. Передавать независимые обратные списки
  вместо механики не требуется.

Фильтры списка эффектов применяются до подсчёта количества и пагинации:
`reference_state=linked|unlinked` выбирает наличие входящих связей,
`reference_type=class|race|...` — тип ссылающейся сущности,
`reference_id=<uuid>` — конкретный класс или вид,
`reference_level=3` — явно заданный уровень. Совместные условия проверяют одну
связь: класс на третьем уровне и вид на пятом не означают выдачу вида на третьем.
Права чтения предметов действуют и для обеих сторон связи.

## Хранение и расширение

Миграция `281_entity_references` создаёт отдельные таблицы узлов и рёбер,
представление разрешённых ссылок, функции извлечения и триггеры библиотечных
таблиц. Она заполняет индекс существующих данных. Сохранённые персонажи,
история боёв и сертификаты не переписываются.

После сверки с продовым снимком от 29 сентября версии этого набора перенесены
на 281–285: в production номера 277–280 уже заняты другими миграциями.
Имена ранних исходных файлов и таблиц аудита классификации сохранены, чтобы
не менять уже применённый локальный манифест и его контрольную сумму.

Идентификаторы из механик разрешаются через зарегистрированные псевдонимы
сущности: UUID, номер карточки и профильные ключи. Явные списки классов учитывают
названия классов; короткие идентификаторы заклинаний следуют существующему
преобразованию английского имени. Устойчивые ключи имеют приоритет, неоднозначное
имя не выбирает произвольную сущность. Переименование или удаление цели отражается
при чтении индекса. Повторный расчёт не добавляет дубликатов.
Рекурсивный обход ограничен полями механик и явными типами ссылок; он не ищет
произвольные совпадения UUID во всём документе.

Новая сущность на существующих полях не требует изменения интерфейса или
извлекателя. При добавлении нового формата поля со ссылкой нужно расширить
декларацию извлечения в `backend/migrations/entity_references_277.sql` через
следующую миграцию и добавить пример второй сущности в тесты.

Динамические метаданные связей исключаются на входе в расчётные каталоги,
хеширование состояний и инструменты экспорта/миграций. Отображение связей и
права читателя не влияют на прежние хеши механик. Замороженная политика
сертификации не изменена.

## Интерфейс

Конструкторы показывают связи текущего черновика; редакторы и карточки деталей —
исходящие и обратные связи с уровнями. Для связанных сущностей используются
общие компоненты карточек, превью и настройки представления их типов.
Во вкладке «Эффекты» доступны фильтры использования, типа и конкретного источника,
уровня выдачи. Категория единственной входящей связи от класса или вида показывает
его имя и, при наличии, уровень. Разделители зависят от `effect_type`; сервер
сортирует группы до пагинации, затем применяет выбранную сортировку внутри группы
и устойчивый ID. Аналогичный порядок применяется к категориям черт.

Локальное применение и проверки описаны в
[`entity-references-local-verification-277.md`](entity-references-local-verification-277.md).
